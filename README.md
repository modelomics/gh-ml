# GitHub ML

A continually refreshed registry of GitHub repositories across machine learning fields. The curated `current` view seeks projects that present a distinct contribution to an ML model, method, or technique. Broad retrieval is preserved in `observations`, while `candidates` can retain qualified review cases such as reproductions, applications, or repositories with paper associations. Those labels and associations alone do not establish novelty.

This is a discovery registry, not a peer-reviewed catalog. The selector is a high-precision text heuristic, not verification: repository self-description cannot establish that a contribution is actually novel, correct, reproducible, or scientifically validated. Its versioned rules screen out common profile, fork, coursework, resource-list, tutorial, and unrelated-utility results from the curated views; broad or excluded retrieval results remain in the append-only `observations` audit history. Review eligibility is not a novelty judgment.

The code lives at [modelomics/gh-ml on GitHub](https://github.com/modelomics/gh-ml). The collector is configured to publish to the [`modelomics/gh-ml` dataset](https://huggingface.co/datasets/modelomics/gh-ml) on the [Modelomics Hugging Face organization](https://huggingface.co/modelomics). **GitHub ML** is the display name; `gh-ml` is the repository and dataset slug. The broad Search catalog currently contains 584 queries (569 existing queries plus 15 additions), is versioned in `config/queries/`, and continues to evolve. The current-view selector is `ml-contribution-v4`.

## Scope and labels

The curated `current` view seeks public repositories across fields that present a distinct contribution to an ML model, method, or technique. A reproduction, adaptation, application, utility, or paper association may be useful discovery context and may appear in `observations` or qualify for human review in `candidates`, but none of those categories alone implies a distinct contribution or novelty. The domain and method labels describe the breadth of the collection; they do not determine inclusion.

Labels are multi-label and may be incomplete. A project can belong to multiple domains and methods. Use lowercase hyphenated slugs and evolve the vocabulary as new areas appear. Suggested domain families include:

- **Methods:** architecture, attention, optimization, training, inference, fine-tuning, distillation, quantization, compression, retrieval, agent, reinforcement-learning, generative-modeling, evaluation, interpretability, safety, robustness, data-centric-ml, federated-learning, privacy, causal-ml, probabilistic-ml, graph-ml, scientific-ml
- **Fields:** natural-language-processing, computer-vision, speech, audio, multimodal, robotics, bioinformatics, computational-biology, chemistry, materials-science, medicine, climate, geospatial, time-series, recommender-systems, cybersecurity, finance, education, physics, mathematics
- **Project kinds:** model, method, technique, dataset, benchmark, paper-implementation, reproduction, application, library, framework, tutorial

These are starting suggestions, not an exhaustive controlled vocabulary. Do not infer a paper-quality novelty judgment from labels or repository popularity.

## Collection and coverage limits

The collector uses a configurable set of GitHub repository search queries. Query design should be intentionally broad, versioned in the repository, and expanded when gaps are found. GitHub REST Search returns at most 1,000 results for an individual search. GitHub also limits a search query to 4,000 matching repositories, applies custom request limits (authenticated repository search is currently limited to 30 requests per minute), and may time out or report incomplete results. The collector records these outcomes in per-query coverage instead of treating partial results as complete. Splitting a crowded search by date, topic, language, domain, or other qualifiers can expose more results, but does not make coverage exhaustive. See the [GitHub search API limits](https://docs.github.com/en/rest/search/search).

The 584-query catalog is intentionally broad retrieval, not the curated `current` view. It produces raw observations with query provenance; `current` is selected separately by `ml-contribution-v4` to seek projects presenting a distinct ML model, method, or technique contribution. Search matches, applications, reproductions, utilities, and paper associations provide discovery context but do not by themselves establish that contribution. Search indexes metadata and text imperfectly; projects may use unexpected terminology, live outside GitHub, be private, be deleted, or not be indexed. Existing results can shift with ranking and indexing. Neither broad retrieval nor the stricter selector is exhaustive. GitHub Search excludes forks by default, and the collector preserves any explicit fork qualifier in a query. The algorithmic-trading query is narrowed to repositories whose README mentions both “algorithmic trading” and “machine learning”.

## Registry record

Each collected row is a repository observation. The collector deduplicates matches within a run by numeric GitHub repository ID. Across daily runs, the Hub stores append-only observations; consumers group by `github_id`, prefer Search observations over topic and census observations, then select the greatest `observed_at` within the chosen source. Keep the following information where available:

| Field | Meaning |
| --- | --- |
| `github_id` | Stable numeric GitHub repository ID; primary deduplication key |
| `name` | Current `owner/repository` name |
| `url` | Canonical GitHub page URL |
| `description` | GitHub repository description |
| `created_at`, `updated_at`, `pushed_at` | GitHub timestamps |
| `stars`, `forks` | Snapshot repository counts |
| `language`, `license`, `topics`, `homepage` | GitHub metadata, nullable or empty when absent |
| `archived`, `fork` | Repository state flags |
| `domains`, `methods` | Multi-label registry tags; lists of slugs |
| `query_ids` | Search queries that discovered this candidate; topic and census observations are queryless |
| `paper_ids` | Hugging Face Daily Papers IDs associated with the repository across raw observations; association is unverified provenance, not proof of an official implementation or novelty |
| `queryless`, `discovery_source`, `topic_names` | Present on topic observations to identify queryless topic retrieval and the matched topic slug |
| `observed_at` | UTC time this metadata snapshot was collected |
| `novelty_signals` | Evidence labels such as `query-match`, `paper-reference`, or `model-weights`; not verified novelty |
| `candidate_status` | Queryless census/topic discovery status (`candidate`, `unknown`, or `not_candidate`); not a novelty judgment |
| `candidate_rule_version`, `candidate_eligible`, `candidate_reason` | Derived candidate-view decision under `ml-candidate-v3`, with its reason; eligibility is heuristic, not verification |

The default `current` dataset contains one latest observation per GitHub ID only when the current `ml-contribution-v4` selector marks it `include`. The `candidates` config retains eligible review cases as well as includes; `observations` remains opt-in raw history. Topic and census observations can contribute to the raw history, but Search observations take precedence when choosing the row used for current selection. These rules are text heuristics, not verification; false positives and missed candidates remain possible.

Null means unavailable or not supplied by GitHub. Preserve the raw GitHub ID even if a project is renamed; URLs and names can change. The current schema records `name`, `url`, and `license`; consumers should not assume first-seen or last-seen fields exist in every row.

## Setup and use

Requirements: Python 3.12 or newer and [uv](https://docs.astral.sh/uv/). The commands below use the `gh-ml` executable (slug `gh-ml`; display name `GitHub ML`).

```sh
uv sync --extra dev
uv run gh-ml --help
uv run gh-ml run --no-publish
```

`run` accepts `--repo`, `--config-dir`, `--output-dir`, `--max-requests`, `--since-days`, and `--no-publish`; use `uv run gh-ml run --help` for the exact defaults. `backfill` accepts `--repo`, `--config-dir`, `--output-dir`, `--start`, `--end`, `--max-requests`, and `--no-publish`. It searches repository creation dates, starting at `2008-01-01` by default, and splits dense date intervals when needed to get beneath GitHub’s per-search result cap. Each invocation respects `--max-requests`, writes per-query or per-query/date-partition coverage, and saves a resumable cursor. Run the same command again to continue until coverage reports the sweep complete. The default output is under `~/.local/share/modelomics-gh-ml/runs`; daily state is `state.json`, and backfill state is `backfill-state.json`.

`historical-sample` accepts `--repo`, `--config-dir`, `--output-dir`, `--max-requests`, and `--no-publish`. It takes one ranked first-page search for each query/year lane from 2008 through a campaign end date fixed when the campaign starts. That end date remains unchanged across partial runs and later runs with an expanded catalog. Its v2 completion ledger preserves completed `(query ID, query text, year)` work across catalog additions and edits: new or changed queries are sampled for every year in the fixed campaign, while removed queries are dropped. A legacy v1 cursor is safely migrated by matching query signatures. The checkpoint is `state/historical-sample.json` on the Hub and `historical-sample-state.json` in local output. Completed ledger entries persist, so future catalog additions resume only their missing lanes. The request budget is spread round-robin across query groups (the scheduled budget remains 200 requests/day). These are ranked first-page samples, not complete repository records; they do not replace date-partitioned historical backfill or guarantee complete coverage.

`backfill-fair` accepts `--repo`, `--config-dir`, `--output-dir`, `--max-requests`, and `--no-publish`. It rotates through query/date-partition work round-robin, issuing one Search request per query in each rotation so a bounded run distributes work across queries. Its checkpoint is independent: `state/backfill-fair.json` on the Hub and `backfill-fair-state.json` in local output. It does not import or migrate the legacy `backfill` cursor (`state/backfill.json` / `backfill-state.json`); the legacy `backfill` command and its checkpoint remain available for historical runs. Do not claim exhaustive coverage until all date partitions have been scanned and coverage records show the completed sweep. For local coverage without publishing, run `uv run gh-ml backfill-fair --max-requests 700 --no-publish` and reuse the same output directory to resume.

The included [GitHub Actions workflow](.github/workflows/daily.yml) defines four bounded Search passes, the queryless census and topic collectors, a bounded README-evidence pass, a bounded Hugging Face Daily Papers collector, and a derived current-view snapshot. The Search request budget is 2,000 by default: breadth sample (500), recent sweep (600), annual historical sample (200), and fair historical backfill (700). Topic breadth is a separate GraphQL collection, configured for up to 68 GraphQL topic pages per daily run: 38 first-page refreshes (one for each topic) plus up to 30 deeper cursor pages. The expanded field topics cover geospatial and remote sensing, bioinformatics and cheminformatics, speech recognition and text to speech, medical imaging, and recommender systems. See [topic breadth](docs/topic-breadth.md) for its catalog, paging, state, provenance, and limitations. Workflow configuration describes intended behavior; this README does not assert that any particular remote run has completed or published. Search and topic coverage and their separate checkpoints make partial progress visible and resumable, but do not establish completeness. The snapshot projection applies `ml-contribution-v4` to current-view rows. The Daily Papers pass uses a bounded recent replay and historical backfill, with a page budget of 20 by default (configurable from 1 to 100). Its user-submitted GitHub links are unverified discovery signals; they do not establish official implementations or inclusion. Paper-link assertions and their source provenance are stored separately under `data/paper-links/`. See [Hugging Face Daily Papers](docs/hf-daily-papers.md) for collection state, budgets, provenance, candidate eligibility, and limits.

Run the breadth sample locally with `uv run gh-ml sample --max-requests 500 --since-days 1`. It uses a local resumable sample checkpoint in the chosen output directory to rotate through the configured catalog; with more queries than the 500-request budget, one run samples only a subset, not every query. Rerun with the same output directory to continue. Add `--no-publish` to keep results local. The separate sample, recent, annual historical-sample, and backfill checkpoints let each pass resume without advancing another pass's progress.

Run the annual historical sample locally with `uv run gh-ml historical-sample --max-requests 200`. It uses the v2 completion ledger in the separate `historical-sample-state.json` checkpoint in the selected output directory; the Hub checkpoint is `state/historical-sample.json`. Completed `(query ID, query text, year)` lanes persist across catalog changes, so added or edited queries fill every year in the campaign, and removed queries are dropped. A v1 cursor is migrated by matching query signatures. The campaign end date stays fixed across partial and expanded runs, and later catalog additions resume their missing lanes. This remains ranked first-page sampling, not a claim that every matching repository has been collected. For fair historical collection without publishing, run `uv run gh-ml backfill-fair --max-requests 700 --no-publish`; its `backfill-fair-state.json` checkpoint resumes independently from the legacy `backfill` checkpoint. The old cursor is not migrated, and exhaustive coverage should not be assumed: completeness requires scanning all date partitions and confirming the coverage records show a completed sweep.

### One-time Papers with Code archive import

The optional `pwc-import` command performs a bounded, resumable local import from the frozen `pwc-archive/links-between-paper-and-code` Hugging Face dataset at revision `56cc5c1938678c33dedebf5f74fc4e62e2c35381` (snapshot dated 2025-07-28). Install its reader with `uv sync --extra pwc`, then run `uv run gh-ml pwc-import --max-rows 10000 --max-repos 500`. Reuse the same output directory to resume. It streams the source, normalizes GitHub links, deduplicates normalized owner/repo names, and resolves current repository metadata through GitHub GraphQL batches of up to 50 repositories. Successful lookups use numeric GitHub IDs and canonical current repository names; nulls and per-alias errors stay pending for retry. It never calls GitHub Search and **never publishes to Hugging Face**. The default output is `~/.local/share/modelomics-gh-ml/pwc-import`; the checkpoint, observation and link JSONL files, and per-run manifests stay there. Each `links-<run-id>.jsonl` file records every valid PWC link assertion scanned in that invocation, including repeated repository links, source row offsets, paper fields, and license provenance. An observation embeds only the first scanned assertion for its repository as a representative; the sidecars preserve the complete assertions across resumed runs. Output records carry source revision and CC-BY-SA-4.0 attribution. The importer is intentionally not part of the daily workflow: the archive is stale and the downstream license decision remains pending. Treat the output as licensed derived material; if sharing adaptations, retain attribution, identify changes, link the license, and follow its share-alike terms.

To build a separate local Parquet snapshot from the four completed import batches, install the Parquet extra and run:

```sh
uv run --extra parquet python -m gh_ml.pwc_snapshot --input-root /mnt/archive/runs/gh-ml-pwc-import-2026-09-24 --output-dir /tmp/gh-ml-pwc-snapshot
```

This writes `repositories.parquet`, `paper_links.parquet`, and a provenance manifest under the output directory. Paper assertions join to repositories only by exact case-insensitive current `owner/repository` name; `paper_links.parquet.github_id` is nullable when no unique current-name match exists. The outputs preserve the pinned Papers with Code archive attribution and CC-BY-SA-4.0 source/license metadata. This workflow is local-only and separate from the main `gh-ml` dataset publication; the PWC-derived material remains out of that dataset pending the user’s license decision.

### Local current view and repository census

To materialize a local current view from an already downloaded dataset, run `uv run gh-ml current-view /path/to/dataset --output ~/.local/share/modelomics-gh-ml/current-view.jsonl`. It reads `data/observations/**/*.jsonl`, writes a deterministic JSONL view and a sibling manifest, and performs no Hub writes. This local command does not load separate README evidence files. Search observations take precedence over topic and census observations for a shared `github_id`; within the chosen source, the newest `observed_at` row supplies the snapshot. The `all_*` fields retain accumulated labels across observations while ordinary fields come from that chosen row. Parquet is optional: install it with `uv sync --extra parquet` and pass `--parquet-output ~/.local/share/modelomics-gh-ml/current-view.parquet`. The configured workflow includes four Search collectors, a bounded README-evidence collector, queryless census and topic collectors, and a snapshot publisher. See [topic breadth](docs/topic-breadth.md) for the topic source. The `observations` config exposes raw observation rows through the Datasets library, while JSONL remains the source history.

The queryless `census-daily` collector uses bounded pages from GitHub's public Core `/repositories` endpoint and enriches returned IDs with repository metadata. It is a complementary discovery stream, not a complete or verified ML census. Its daily budget is 50 pages; a full walk through GitHub's repository-ID history would take years at that rate. Search-derived observations take precedence when an ID appears in both streams. Census collection stores its append-only observations, durable cursor/state, and page coverage on the Hugging Face dataset. For a bounded local run without Hub access, pass `--no-publish`: `uv run gh-ml census-daily --work-dir ~/.local/share/modelomics-gh-ml/census --max-pages 50 --no-publish`. Each invocation creates a fresh run directory; `--no-publish` does not resume from Hub state. Scheduled runs resume from the durable cursor and state on the dataset Hub. See the [census guide](docs/census.md) for coverage, selection, and the Zipline example.

The older `census` command remains a local-only bounded collector with its own `--output-dir` and `--since` options. For example, `uv run gh-ml census --max-pages 2` writes locally and does not publish its results to the dataset. It is separate from the scheduled `census-daily` workflow and its Hub-backed cursor.

The local `current-view` command prefers Search observations over topic and census observations for each GitHub ID, then chooses the latest row within that source, adds `first_observed_at`, `observation_count`, and sorted unions of accumulated labels, and computes versioned text evidence and selection fields. It does not load the separate README evidence files. Selection uses repository name, description, and topics, plus available compact README signals in the published projection; query matches and labels are retained as provenance but cannot satisfy the selector. The versioned selector assigns `include`, `review`, or `exclude`; the published `current` Parquet contains only `include` rows, while qualified review rows can appear in `candidates`. The opt-in `repositories` config at `data/repositories/repositories.parquet` contains one selected current-view row per numeric GitHub ID when `fork` is exactly false (Search observations take precedence over topic and census observations; the latest row within that source is selected), independently of novelty selection. It is not a verified novel ML set and does not group complete fork families. The selector seeks distinct contribution claims, but repository text does not verify novelty.

For a blinded human audit of selector quality, see the [evaluation protocol](docs/evaluation.md). It covers probability sampling, independent annotation, primary evidence, adjudication, restricted scoring keys, and interpretation limits.

CLI help: `uv run gh-ml --help`, `uv run gh-ml current-view --help`, `uv run gh-ml publish-current-view --help`, and `uv run gh-ml census-daily --help`.

GitHub Actions supplies `GITHUB_TOKEN`. The seed and backfill observations are merged on `main`, and the dataset is publicly loadable. The daily workflow is active; a manual run completed and published four collection updates. Hugging Face Trusted Publisher authentication is configured for repository `modelomics/gh-ml`, branch `main`, and workflow `daily.yml`. The workflow requests `id-token: write` and uses `HF_OIDC_RESOURCE=datasets/modelomics/gh-ml` to exchange its GitHub identity for a short-lived Hugging Face token. See [Hugging Face Trusted Publishers](https://huggingface.co/docs/hub/trusted-publishers). If `HF_TOKEN` is set, it takes precedence over OIDC. For local publishing, authenticate GitHub either by exporting `GITHUB_TOKEN` or by signing in with `gh auth login` (the CLI can read `gh auth token`). Authenticate Hugging Face either by exporting `HF_TOKEN` or by running `uv run hf auth login`; the collector reads the saved Hugging Face CLI token. The HF token needs write access to the dataset. `--no-publish` only writes local output and does not require an HF token. Never commit tokens, local `.env` files, or generated data. Inspect `coverage/<run-id>.json` for capped searches, incomplete results, errors, or request-budget pauses; a successful sweep is not proof of exhaustive GitHub coverage.

The Hub checkpoints are the recovery source for scheduled and manually dispatched Actions runs. For local recovery after an interrupted run, keep and reuse the same `--output-dir` so its cursor resumes. To begin a clean local collector state instead, choose a new output directory. GitHub scheduled workflows run only from the default branch, can be delayed or dropped during high Actions load, and are automatically disabled in public repositories after 60 days without repository activity. Use **Run workflow** in Actions to resume collection; see [GitHub schedule event details](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Local output and generated run artifacts belong outside version control. The `.gitignore` excludes local `data/` and JSONL/Parquet outputs. See the dataset card in [`dataset/README.md`](dataset/README.md) for the intended Hub file layout and examples for loading the Parquet configurations and inspecting coverage.
